## Context

ADR-007 selected an explicit actor-context model that distinguishes:

- `triggeredBy` / `requestedBy`: who or what initiated the work;
- `performedBy` / `processedBy`: who or what executed the work.

The existing `AuditLog.actorId` behavior should remain compatible for authenticated human user actions. The gap is that system/worker/operator context should not live only in free-form details when it is needed for reliable audit classification.

The original follow-up goal was to add a concrete audit representation so audit rows can distinguish `triggeredBy` from `performedBy` without relying only on free-form details.

## Goal

Define and implement the minimal structured audit actor context representation needed for current and near-term SaPen Annotate auditability.

The implementation should let future RB-116 classify audit rows and mutation paths using stable fields or a documented structured shape.

## Non-Goals

- Do not redesign the entire audit system.
- Do not replace existing `AuditLog.actorId` human-user attribution.
- Do not force all domain rows to use `AuditLog` if append-only domain rows are the proper audit artifact.
- Do not implement unattended worker authentication; see RB-115-B.
- Do not implement Core handoff provenance; see RB-115-C.
- Do not build audit UI.
- Do not complete or fabricate RB-113 iPad evidence.

## Required Decision

Before code changes, inspect the current Prisma schema and audit helpers and choose one of these implementation paths:

### Option 1 - Typed AuditLog Fields

Add explicit nullable fields to `AuditLog`, for example:

- `triggeredByUserId`
- `triggeredByActorType`
- `triggeredByActorLabel`
- `performedByActorType`
- `performedByActorLabel`
- `processorId`
- `processorRunId`
- optional `externalActorLabel` / `externalRequestId` only if already needed

Use enums or constrained strings only if the repo conventions make this low-risk.

### Option 2 - Documented Structured `details` Shape

Keep the schema unchanged but define and test a structured JSON shape inside existing details/provenance fields, for example:

```json
{
  "actorContext": {
    "triggeredBy": {
      "type": "USER",
      "userId": "...",
      "label": "..."
    },
    "performedBy": {
      "type": "SYSTEM",
      "label": "export-worker",
      "processorId": "...",
      "processorRunId": "..."
    }
  }
}
```

This is acceptable only if:

- it is validated by helpers/tests,
- it is documented,
- and RB-116 can reliably classify audit rows from it.

### Option 3 - Hybrid

Use existing `actorId` for the primary human actor and structured details for performedBy/system processor context.

This may be the safest near-term option if schema churn is not justified.

## Requirements

- Preserve existing human-user audit consumers.
- Preserve existing `AuditLog.actorId` meaning for ordinary authenticated user actions.
- Add or update audit helper functions so new code does not manually assemble inconsistent actor context.
- Define canonical actor type values aligned with ADR-007, such as:
  - `USER`
  - `OPERATOR`
  - `SYSTEM`
  - `WORKER`
  - `EXTERNAL_SYSTEM`
- Define canonical labels for current system/worker contexts only where needed, for example:
  - `export-worker`
  - `storage-cleanup`
  - `prediction-import-worker`
- Document which fields/details are required vs optional.
- Ensure no secrets, passwords, tokens, signed URLs, or raw headers are written into actor context.
- Add tests for:
  - ordinary human user audit row remains compatible,
  - user-triggered worker action can represent both triggeredBy user and performedBy worker,
  - operator-triggered script action can include operator/system context without secrets,
  - structured actor context validation rejects malformed values if helper validation exists.
- Update audit docs and ADR-007 follow-up notes.

## Acceptance Criteria

- Audit actor context representation is explicitly documented.
- Existing human-user audit records and consumers remain compatible.
- New or updated audit helper(s) support `triggeredBy` and `performedBy` semantics.
- RB-116 can reference the chosen representation in its matrix/guard.
- No anonymous production write path is introduced.
- Any schema migration, if added, has tests and safe defaults for existing rows.
- RB-113 remains open unless real physical iPad evidence was provided separately.
